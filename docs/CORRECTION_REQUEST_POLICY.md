# Correction Request Operating Policy
# 수정 요청·제보 운영정책

이 문서는 PlannerDesk의 수정 요청·제보 기능 운영 기준을 정리한 정책 문서입니다.  
현재 동작과 향후 DB화 기준을 분리해 기록하며, 기능 구현 문서가 아닌 운영/안전 기준 문서입니다.

## 1) 목적

- 수정 요청·제보 기능은 보험사 링크, 전화번호, 팩스, 청구서류, 공시/약관 링크 등 실무 정보 오류를 제보받기 위한 기능입니다.
- PlannerDesk는 제보 내용을 즉시 공개 정보에 반영하지 않습니다.
- 모든 제보는 관리자 검수 후 반영합니다.
- 현재 MVP는 DB 저장 없이 클립보드 복사 기반으로 운영합니다.
- 향후 DB화는 별도 고위험 PR로 분리합니다.

## 2) 제보 가능한 항목

- 보험사 전산 링크 오류
- 보험사 고객센터 번호 오류
- 전산 헬프데스크 번호 오류
- 인콜/모니터링 번호 오류
- 청구 팩스 번호 오류
- 등기우편 주소 오류
- 약관 링크 오류
- 청구양식 링크 오류
- 공시/약관 공식 링크 오류
- 청구서류 명칭 또는 분류 오류
- 카드납 가능 여부 정보 오류
- 지원 브라우저 정보 오류
- 오탈자 또는 UI 표시 오류
- 공식 출처 변경 제보

## 3) 제보 금지 항목

아래 항목은 입력/제보를 금지합니다.

- 고객 이름
- 주민등록번호
- 휴대폰 번호
- 주소
- 이메일
- 계약번호
- 증권번호
- 계좌번호
- 병명
- 진단명
- 진단서
- 처방전
- 진료기록
- 검사결과지
- 입퇴원확인서 원본
- 수술확인서 원본
- 보험금 청구서 원본
- 고객 의료자료
- 고객 개인정보가 포함된 사진 또는 파일
- 보험금 지급 가능 여부 판단 요청
- 보험금 지급 금액 산정 요청
- 손해사정 판단 요청
- 의료 진단 해석 요청
- 특정 고객의 청구 가능성 판단 요청

## 4) PlannerDesk가 하지 않는 것

- PlannerDesk는 보험금 지급 여부를 판단하지 않는다.
- PlannerDesk는 보험금 지급 금액을 산정하지 않는다.
- PlannerDesk는 손해사정 업무를 수행하지 않는다.
- PlannerDesk는 의료 진단을 해석하지 않는다.
- PlannerDesk는 고객 의료서류를 처리하지 않는다.
- PlannerDesk는 고객 개인정보 저장을 기본 전제로 하지 않는다.
- 공식 링크, 연락처, 서류 기준은 공개 전 공식 출처 확인이 필요하다.
- 본 자료는 설계사 실무 참고와 업무 정리를 위한 용도다.

## 5) 제보 처리 원칙

아래 상태명은 **향후 설계 참고용**입니다. 이번 PR에서 enum/DB 모델을 만들지 않습니다.

- `received`: 제보 수신
- `triage`: 검토 대기
- `needs_official_source`: 공식 출처 확인 필요
- `accepted`: 반영 가능
- `rejected`: 반영 불가
- `resolved`: 처리 완료
- `archived`: 보관 종료

운영 원칙:

- 제보는 접수 즉시 공개 데이터를 변경하지 않습니다.
- 관리자 검수와 공식 출처 확인 이후에만 반영할 수 있습니다.
- 반영 여부와 근거를 내부 운영 기준에 따라 기록합니다.

## 6) 검수 원칙

### 반영 가능 조건

- 공식 보험사 홈페이지에서 확인 가능
- 공식 공시/약관/청구 안내 페이지에서 확인 가능
- 보험사 공식 고객센터 또는 전산 헬프데스크 안내와 일치
- 내부 운영자가 공식 출처를 확인
- 고객 개인정보나 의료자료가 포함되지 않음
- 보험금 지급 판단으로 보이지 않음

### 반영 불가 조건

- 출처가 불명확함
- 블로그, 카페, 커뮤니티, 개인 경험담만 근거로 함
- 특정 고객의 청구 결과를 근거로 일반화함
- 고객 개인정보 또는 의료자료 포함
- 보험금 지급 가능성 판단 요청
- 손해사정성 판단 요청
- 의료 진단 해석 요청

## 7) 향후 DB화 시 원칙

이번 PR에서는 구현하지 않습니다. 향후 DB화 이전에 아래 기준을 만족해야 합니다.

- 데이터 최소 수집
- 고객 개인정보 입력 차단
- 의료자료 업로드 차단
- 파일 업로드 금지
- 신고/제보 내용 서버 검증
- 금지어 또는 민감정보 패턴 검사
- 관리자 검수 전 공개 반영 금지
- 보관 기간 정의
- 처리 완료 후 삭제 또는 비식별화 기준 정의
- rate limit 또는 spam 방지 검토
- audit log 검토
- 관리자 권한 분리 검토

## 8) UI 문구 가이드

제보 UI에서 사용할 수 있는 문구 예시:

- 잘못된 링크나 연락처를 발견했다면 제보해주세요.
- 고객 개인정보, 의료자료, 진단서, 청구서류 원본은 입력하지 마세요.
- 제보 내용은 관리자 검수 후 반영됩니다.
- 보험금 지급 여부나 지급 금액 판단 요청은 처리하지 않습니다.
- 공식 출처 확인 후 업데이트됩니다.

## 9) 관리자 검수 체크리스트

- [ ] 공식 출처 확인 여부
- [ ] 제보 항목 분류
- [ ] 고객 개인정보 포함 여부
- [ ] 의료자료 포함 여부
- [ ] 보험금 판단 요청 포함 여부
- [ ] 손해사정성 표현 포함 여부
- [ ] 반영 대상 데이터 확인
- [ ] 공개 전 검수 상태 설정
- [ ] 변경 이력 기록 필요 여부
- [ ] 반영 후 재검토 일정 필요 여부

## 10) 향후 PR 분리 기준

아래 작업은 별도 고위험 PR로 분리해야 합니다.

- CorrectionRequest Prisma 모델 추가
- DB migration
- 관리자 제보 큐 구현
- 제보 저장 서버 액션 구현
- 이메일 발송
- 파일 업로드
- 사용자 계정 기반 제보 이력
- rate limit
- spam 방지
- 민감정보 자동 탐지
- audit log
- 권한/RBAC 확장

## 부록: 현재 MVP와 향후 DB화 구분

- 현재 MVP: 클립보드 복사 기반, DB 미사용, 관리자 큐 미구현
- 향후 DB화: 별도 고위험 PR에서 보안/개인정보/권한 기준 검토 후 진행

관련 DB화 사전 설계 문서는 `docs/CORRECTION_REQUEST_DB_PLAN.md`를 참고한다.
